# Gateway 动态路由

网关从 Nacos 的 `cloud-gateway-routes.json` 加载业务路由，与业务 YAML 使用相同的命名空间、`NACOS_GROUP` 和鉴权。默认 public / `LAB_GROUP`；Data ID 格式选择 JSON。完整初始配置见 [样例](nacos/cloud-gateway-routes.json)。独立 Compose 会补齐该配置，复用现有中间件时需要自行发布。

## 配置格式

```json
[
  { "id": "user-service", "path": "/api/users/**", "uri": "lb://cloud-user" },
  { "id": "order-service", "path": "/api/orders/**", "uri": "lb://cloud-order" }
]
```

每条定义只接受三个字段：

| 字段 | 约束 |
| --- | --- |
| `id` | 小写字母开头，其余为小写字母、数字或短横线，最长 64 位，整份配置内唯一 |
| `path` | 只能匹配 `/api/users`、`orders`、`products`、`stocks`、`notifications` 业务路径；支持合法 Spring 路径模式 |
| `uri` | `lb://cloud-...` 服务名，通过相同 Nacos 命名空间和 Group 发现上游；不接受外部 HTTP URL |

数组顺序决定匹配优先级，最多 50 条，配置长度最多 65536 个字符。统一移除第一段 `/api`，不接受任意过滤器、路径重写或管理接口路由。匹配顺序靠前的精确路由可以覆盖后面的通配路由。

上游服务名通过格式校验不代表服务一定存在。若服务没有可用实例，请求仍返回 503；这允许通过切换服务名观察真实路由行为。原 `gateway.routes.*-uri` 和 `GATEWAY_ROUTES_*_URI` 不再控制路由，应在此 JSON 中修改上游。

## 生效与故障行为

首次启动读取配置并注册监听，缺失、空白或无效配置会阻止网关启动，不静默使用旧的固定路由。运行中更新先解析并构建完整快照，通过后才替换当前快照并发布 Gateway 缓存刷新事件；无需暴露 Actuator 的路由管理接口。

运行中格式错误、重复 ID、未知字段或非法路径、URI 会被拒绝，当前路由保持有效。日志记录更新成功或拒绝及路由数量，不记录配置全文。在请求已经选中路由后发生的更新，不改变该请求已选择的上游；新请求在缓存刷新完成后使用新配置。

`[]` 表示明确关闭全部业务路由，相关请求返回 404。删除 Data ID 或发布空白内容不会等价于 `[]`：运行中的网关拒绝该更新并保留快照，但后续首次启动会失败。进程内的旧快照不会覆盖 Nacos；若发布了无效配置，需要修复 Nacos 后再重启。

## 手工验证

1. 启动用户、商品和网关，确认 `/api/users/1`、`/api/products/1001` 均返回 200。
2. 将商品通配路由替换为 `/api/products/1001`，发布后确认商品 1001 可访问，1002 返回 404；验证新增与删除。
3. 将用户路由的 URI 改为不存在的 `lb://cloud-user-missing`，发布后返回 503；恢复后返回 200。只在独立实验环境操作。
4. 发布重复 ID 或非法 JSON，等待网关“更新被拒绝”日志，确认上一步有效路由继续可用；然后修复配置。
5. 保留一份有效的精确路由并重启网关，核对配置自动加载。
6. 发布 `[]`，核对业务路径返回 404；恢复完整样例，核对五类业务路由恢复。

每次发布后等待更新日志及实际请求结果，不能仅凭 Nacos 显示发布成功认定路由已经生效。更新期间可以并发访问未改变的用户路由，观察是否存在半份路由或短暂丢失。

2026-10-13，基于独立 Compose 实际验证了路由新增、删除、上游修改、网关重启加载、空数组关闭与恢复；非法 JSON、重复 ID、管理路径、外部 URL 和未知字段均保留旧路由。四次完整配置替换期间，80 次并发用户请求全部成功。无效初始配置拒绝启动，最终六服务 LOCAL / GLOBAL 幂等下单及通知消费回归通过。
